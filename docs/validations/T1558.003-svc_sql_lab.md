# Bounded validation: ATT&CK T1558.003 — Kerberoasting

## Objective and proof condition

Validate visibility for a single Kerberos service-ticket request associated with the synthetic account `svc_sql_lab`.

Stop when one domain-controller Security event **4769** is found in the validation window where:

- `ServiceName` is the exact SPN selected from `svc_sql_lab`;
- the requester/client fields match the dedicated test session and host; and
- `TicketEncryptionType` is recorded and decoded.

This procedure does **not** crack, export, reuse, inspect, or transmit ticket or credential material. It creates no persistence and makes no configuration changes.

## Fixed scope guard

The accompanying script contains this immutable allowlist:

```powershell
$AllowedAccounts = @('svc_sql_lab')
```

The operator supplies an SPN, but the script resolves that SPN in Active Directory and aborts unless it belongs to the sole allowlisted account. It requests exactly one service ticket.

## Preconditions

- Disposable, egress-disabled Active Directory lab.
- A fresh, dedicated interactive logon session on a domain-joined test host. Do not use an administrator's normal session.
- RSAT Active Directory PowerShell module on the test host.
- Read access to the DC Security log and successful auditing for **Kerberos Service Ticket Operations**.
- Known DC hostname supplied to the script.
- Clock synchronization.
- No pre-existing cached ticket for the chosen SPN. Run `klist` first; if present, end the dedicated session and start a fresh one. Do not purge a normal working session.
- Record the test host, requester identity, DC, UTC start time, change/ticket reference, and chosen SPN.

## Execute

1. Confirm the account and its registered SPNs without changing it:

   ```powershell
   Get-ADUser -Identity svc_sql_lab -Properties ServicePrincipalName,msDS-SupportedEncryptionTypes |
     Select-Object SamAccountName,ServicePrincipalName,msDS-SupportedEncryptionTypes
   ```

2. Choose exactly one SPN returned above. Prefer the intended synthetic SQL SPN, for example `MSSQLSvc/sql-lab.example.test:1433`. Never invent an SPN.
3. From the fresh dedicated session, run:

   ```powershell
   .\Invoke-T1558_003-SvcSqlLab.ps1 -ServicePrincipalName 'MSSQLSvc/sql-lab.example.test:1433' -DomainController 'dc01.example.test'
   ```

4. Preserve the script's structured output with the test record. Do not save Kerberos tickets or process memory.

The script requests a ticket through the Windows Kerberos security provider and then reads only event 4769 from the named DC, constrained to the recorded UTC window and exact SPN.

## Encryption-type interpretation

Use the `TicketEncryptionType` value in event 4769:

| Value | Meaning | Assessment |
|---|---|---|
| `0x12` / 18 | AES256-CTS-HMAC-SHA1-96 | Preferred |
| `0x11` / 17 | AES128-CTS-HMAC-SHA1-96 | Acceptable |
| `0x17` / 23 | RC4-HMAC | Remediation required |
| `0x03` / 3 or `0x01` / 1 | DES | Fail; remove immediately |

Windows versions may render the field in hexadecimal or decimal. Preserve the raw event XML alongside the decoded assessment.

## Expected telemetry

Primary proof:

- **4769** on the issuing DC: Kerberos service ticket requested. Correlate exact SPN, requester, client address, timestamp, status/failure code, ticket options, and encryption type.

Supporting telemetry, when enabled:

- **4688** on the test host: PowerShell process creation.
- PowerShell Operational **4104**: script-block logging.
- **4770** on a DC only if a ticket renewal occurs; it is not required and should not occur in this single-request test.
- **4768** is a TGT request and is not required in a fresh session that already has a TGT.

Absence of 4769 is a telemetry failure or indicates the SPN ticket was already cached; do not repeat blindly. Check auditing, DC selection, time sync, and session freshness before one controlled retry.

## Detection guidance

Alert or hunt on 4769 using service-account and SPN context, not encryption alone:

- RC4 (`0x17`) service tickets where AES should be supported.
- A single requester obtaining tickets for many distinct SPNs or service accounts in a short window.
- Bursts above that requester's baseline, especially from workstations that do not normally access those services.
- Requests for high-value service accounts, unusual client addresses, or anomalous ticket options/failure codes.
- Downgrades where the account and KDC support AES but the issued ticket is RC4.

Suppress known service behavior only with bounded host, account, SPN, and time-window exceptions. Keep raw 4769 telemetry long enough to baseline distinct-SPN counts and encryption transitions.

Example Microsoft Sentinel KQL starting point:

```kusto
SecurityEvent
| where EventID == 4769
| extend Enc = tostring(column_ifexists("TicketEncryptionType", "")),
         SPN = tostring(column_ifexists("ServiceName", "")),
         Client = tostring(column_ifexists("IpAddress", ""))
| summarize Requests=count(), DistinctSPNs=dcount(SPN),
            RC4=countif(Enc in ("0x17", "23"))
  by Account, Client, bin(TimeGenerated, 10m)
| where RC4 > 0 or DistinctSPNs >= 10
```

Tune the threshold from lab and production baselines.

## Remediation

- Migrate conventional service accounts to **gMSA** where the application supports it. Restrict which hosts may retrieve the managed password and validate service compatibility before cutover.
- Ensure the service, clients, account, and domain controllers support AES. Configure the account for AES128/AES256 and remove RC4 only after dependency testing.
- After enabling AES on a legacy account, perform a controlled password rotation so AES keys are generated; coordinate service restart/redeployment.
- Remove stale or duplicate SPNs, enforce least privilege, deny interactive logon for service identities, and monitor delegation settings.
- Do not merely select “AES supported” while leaving an application pinned to RC4; verify the post-change 4769 encryption value.

## Cleanup and telemetry preservation

1. Stop immediately after the first matching 4769 is captured.
2. Export only the relevant event record/XML and operator transcript to the lab evidence store; do not export ticket caches, LSASS material, or credentials.
3. End the dedicated test logon session to destroy its Kerberos cache. Use `klist purge` only if the session is disposable and ending it is impractical; it purges that session's tickets broadly.
4. Confirm no files containing ticket material were created (the supplied script creates none).
5. Retain DC and endpoint logs per the exercise evidence policy.
6. Record outcome as pass (4769 plus encryption type), telemetry gap, or remediation required. No further ticket requests are needed.
